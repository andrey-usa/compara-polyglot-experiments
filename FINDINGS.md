# Findings

What this project has established, as tables. The repository's history was
squashed; this file is what it taught, so that it can be read without the
history and acted on without repeating it.

## How to read this file

- **Every row has a stable ID**, and IDs are never reused or renumbered: `A-`
  advance (a change that measurably moved speed, memory, correctness or
  coverage), `M-` mistake not to repeat, `T-` technique (who has it, what it
  was worth), `R-` real-world result, `E-` open experiment. Cite IDs in commit
  messages and pull requests; add a row, with the next free ID, when a change
  teaches something.
- **Before starting a change**, search this file for the technique (the `T-`
  table says which ports have it and what it measured) and for the trap (the
  `M-` table says what went wrong before and the rule adopted).
- **Numbers are verbatim** from the record they came from, with their host and
  size where known. They come from many hosts and sittings and are **not
  comparable across rows**; compare rows within one table only (M-007, M-056).
- **Ref** is the pull request or commit in the development history that the row
  came from (kept so a maintainer can trace it), or the compara release whose
  changelog states it.
- The Rust port is compara; rows before 2026-10-09 call it "Rust", and its
  environment variables were then `CSVDIFF_*` (now `COMPARA_*`).

## Where compara stands (2026-10-15)

- **Real-world Parquet** (R-002, R-003): compara is the only port that reads every
  file pyarrow, Polars, DuckDB and pandas write by default on its columnar path,
  with the CSV answer. C and C++ refuse every one (typed columns; Polars' zstd),
  and Zig reads them through its row reader. The C lead in the generated-data
  tables does not carry over to files users bring (M-149).
- **Against DuckDB, Polars and pandas** (R-003, R-004, R-006): on the real
  writers' Parquet, at 1M rows, compara is 3.6-4.8x faster than the fastest of
  the three counting, and 1.9-2.7x writing the rows as CSV, with the same
  answer; on CSV and TSV it writes the rows 2.1-3.0x faster than the fastest
  of them, though its text-path export is the slower half of its own work (E-002).
- **On a GitHub runner** (R-008), every port built for it: the four ports tie on
  CSV and TSV (0.11-0.12 s at 1M rows), and on the real writers' Parquet compara
  counts in 0.26-0.29 s against Polars' 0.78-0.87 s, DuckDB's 1.76-2.83 s and
  Zig's row reader at 1.23-2.13 s.
- **TSV** (R-005): the same answer and the same speed as CSV in every port.
- **Generated data** (the README's 2026-09-30 table and the "Where another port
  leads compara" table below): within 1.18x of the fastest port on CSV, a tie on
  ndjson, 1.10x behind C on Parquet, and Zig spends the least CPU on text.
- **The release binary is the measured binary** (A-135): compara chooses AVX2 at
  run time, so a baseline x86-64 build scans as fast as one built for the runner
  (10M rows: 0.86 s either way on CSV, 2.32 s against 2.31 s on ndjson), and the
  benchmarks now build it the way it is installed.

## Real-world files

Every other table in this repository was measured on files this project's
generator wrote, and its Parquet is a particular kind: every column a string,
uncompressed or snappy, the layout the readers were built around. External
testing on the maintainer's own files (R-007) showed that was not the Parquet
users bring, so `scripts/realworld.py` writes one generated pair every way it
arrives in practice — as CSV, as TSV, and as Parquet from pyarrow, Polars,
DuckDB and pandas, each with its defaults — and asks every port and DuckDB,
Polars and pandas the same question on every file, holding every answer to the
Rust port's on the CSV. `realworld.yml` runs it weekly and on demand.

The tables below are one sitting: `Intel(R) Xeon(R) Processor @ 2.10GHz`, 4 cores, 1M rows
a side, 4 threads for every tool, best of 3, 2026-10-15. C and
C++ were built by their Makefiles with `-march=native` and Zig for the host CPU;
compara is the baseline x86-64 build that `cargo build --release` gives and its
releases ship, which then had no AVX2 scanner. Built for this CPU
(`-C target-cpu=x86-64-v3`), compara counted the wide CSV pair in 0.119 s against
0.137 s for the baseline build — paired median 1.17x, middle half 1.10-1.19x,
nine rounds after the table; TSV 1.13x; with `--export-dir` 1.06x — which is
level with C. The baseline build has chosen AVX2 at run time since (A-135), which
closes that gap. Two shapes: **wide**
is the standard twenty columns keyed on `(account_id, txn_id)` with `updated_at`
ignored; **narrow** is five columns keyed on two integers (`id, k2`, comparing
`amount, name, status`) with B shuffled against A. Each cell is wall · peak RSS
(including the mapped input); the contenders' numbers include starting Python
and importing the library, which their users pay too. **Bold** is the fastest
in the row. Compare rows within these tables only.

### R-005 — TSV costs what CSV costs

Wide shape, counts only, TSV against CSV in the same sitting: C 0.11s against 0.12s; C++ 0.13s against 0.13s; compara 0.15s against 0.15s; Zig 0.14s against 0.15s; DuckDB 4.04s against 4.04s; Polars 1.80s against 1.70s; pandas 19.73s against 19.68s. Every port takes the separator from the
header line, so TSV is the CSV scanner with a different byte; `parity.yml` holds
each port's TSV answer to its CSV answer.

### R-006 — One answer, every tool

DuckDB, Polars and pandas are given the same rules as the ports — the first row
of a repeated key joins, text read as text, a missing value equal only to a
missing value — and every tool that read a file returned the reference counts
on it. A table where the fastest tool gives a different answer would not be a
result; the harness prints such a cell as one and fails the run if compara is
the tool.

### R-007 — External testing that prompted this (2026-10-15)

Measured outside this repository, on the maintainer's machine, two threads per
tool (`compara compare A B -k id,k2 --threads 2`, DuckDB `SET threads=2`,
`POLARS_MAX_THREADS=2`), keys `id, k2`, compared `amount, name, status`; wall ·
MB. First run, Parquet: compara columnar path with rows only in the HTML report
0.30s / 169 MB; DuckDB 0.47s / 156 MB (0.58s loading tables first); Polars
0.67s / 507 MB; pandas 1.58s / 647 MB; DataComPy 2.73s / 708 MB; compara with
CSV row files, which then meant `--engine turbo`, 0.68s / 176 MB. Rerun with row
files from every tool — CSV: compara 0.33s / 137 MB, Polars 0.84s / 480 MB,
DuckDB 0.90s / 322 MB, the Go csvdiff tool 1.48s, pandas 3.13s, DataComPy 7.28s;
Parquet: compara columnar (rows only in HTML) 0.50s / 192 MB, Polars 0.81s,
DuckDB 0.86s, compara row reader with CSV rows 0.90s / 195 MB, pandas 2.47s,
DataComPy 5.70s. The verdict was that on Parquet with CSV row output compara was
level with DuckDB and Polars, not ahead. A-131 (row files from the columnar
path) and A-132 (zstd on the columnar path) are the answer; R-004 measures it.

### Reading of the above

1. **CPU on text is the one consistent lead another port holds.** Zig uses the least
   CPU on CSV and ndjson in every current table (3.0s against 4.0s at 10M CSV, 6.7s
   against 8.6s on wide ndjson). The documented difference is T-013: Zig sweeps each
   file on one thread because splitting measured worse in Zig. Nobody has measured the
   same switch in Rust.
2. **C leads Parquet by 1.10–1.26x on wall.** The one technique C has and compara lacks
   on that path is T-036 (slot table on huge pages), measured as the largest single
   change in C's Parquet path but a loss on another host. The other recorded
   difference is a compare-loop phase gap with no technique attached.
3. **Wide ndjson (100 columns) is where compara trails most on text: 1.14–1.19x.**
   The name-compare inlining (T-019) every other port has was judged neutral for Rust
   at 20 columns only.
4. **The shipped binary was not the measured binary; since A-135 it is.** Every Rust
   number above was built for x86-64-v3, and compara's releases are baseline x86-64
   (T-093). They now choose AVX2 at run time, and at 10M rows the release-style build
   and the `+avx2` build are level on CSV, TSV and ndjson.

### The field, measured once (2026 survey)

The tools people reach for, run on the same comparison (their rows are in the
table above). Four of eight could not do 10M at all.

**Two independent SQL engines make the identical mistake**, to the row. The
inflation is a property of the operator, not the engine — picking a better one
does not change it.

**Nothing in the field reports duplicate keys.** They fold them in silently or
multiply them into the answer. This project joins on the first occurrence,
counts keys rather than rows, and reports duplicates as their own section.

### Techniques, worth it and not

#### Worth it

| Technique | Verdict |
|---|---|
| **The byte-level design** — map the file, a field is one 64-bit word (40-bit offset, 23-bit length, escape bit), nothing becomes a string | the whole reason this class survives at 10M: memory grows with the number of rows, not the bytes in them |
| **SWAR** — find a byte in eight with `(diff - 0x0101…) & ~diff & 0x8080…` | no intrinsics, no feature detection, and it **ties the Vector API at 10M and beats it by 19% at 20M** |
| **Reading Parquet natively, columnwise** | 23.25s → 4.89s on the same comparison. The win is not a faster parser: with both dictionaries interned into one id space, comparing a cell becomes `int32 != int32` |
| **Chunked parallel sweep, ordered insert** | quote parity finds row boundaries mid-file — every `"` toggles state, a doubled quote toggles twice — so parsing splits while first-occurrence-wins stays deterministic |
| **Parallel join over key ranges** | the actual long pole: 20M from 54.60s (2 threads) to 33.32s (4), 2.53x cpu/wall |
| **Sizing the hash table once** | thirteen rehashes at 10M, each a full pass of random probes, gone |
| **Software prefetch at distance 24** | every insert is a cache miss on a table too big to hold, and the hash is already in hand |
| **Threading the generator** | 2.3x to 2.8x on wall for no more CPU -- flat on CSV, 12% *down* on ndjson. This was in the "not worth it" table above on the strength of a comparison that turned out to be unsound; it was a scope decision recorded as a measurement |
| **Framing ndjson rows on the newline byte alone** | valid JSON cannot hold a raw control character in a string, so the quote-tracking scan the row end used was guarding against something the format forbids: 1.58x wall and 1.72x CPU on ndjson, with about twenty string walks a row removed |
| **Stopping the key-only JSON parse once the keys are found** | needs the key columns to be first-wins in both parses, or the two disagree about a row's key and the lookup misses its own row |
| **Deriving `added` instead of counting it** | the join ran a second full pass over a second random-probed table to produce one number that the first pass already implies: 1.31x on CSV, 1.44x on Parquet. Guarded by `CSVDIFF_VERIFY_ADDED=1`, which runs the removed pass and refuses a disagreement |
| **A tag in the index slot, text path** | the Parquet index had it and the text index did not: 1.26x on CSV and 1.20x on ndjson, with the table the same four bytes a slot, because rejecting a collision cost two dependent misses that the loaded word can settle |
| **Reading only the key columns where only keys are read** | C's CSV path: 2.66x at two million rows, **3.65x at ten million** — the gain grows with the size, because past cache the parses removed were memory traffic and not only instructions |
| **Huge pages for rare, long-lived, randomly-probed allocations** | a 128 MB slot table is 32,768 4 KB pages against ~1,500 TLB entries — on the host that measured it; see the row below, where the same change loses on another machine |
| **Writing the generator's two sides at once** | 2.0x on Parquet by itself, where splitting a row group's twenty columns — the split the design points at — is 1.28x |
| **Proving an ndjson row unchanged the same way** | the hazard the CSV proof was gated against, solved rather than avoided: the proof only stands when the rows agree through the last compared value, so what follows is the trailing ignored columns -- a few bytes, in which every quote is a candidate name and one lookup each settles whether a duplicate could override anything. **1.29x of CPU** against a 1.47x ceiling measured first with an unsound build |
| **Proving a CSV row unchanged from its raw bytes** | rows that match usually match because they are the same row with one column moved, so agreeing byte for byte through the byte that closes the last compared column proves every compared column equal and the mate is never parsed: **1.48x wall, 1.52x CPU** at two million rows. It refuses on headers that order columns differently, on a mate whose field carries on where this one stopped (`cc` against `cccccccc`, or a doubled quote), and, until the tail scan below, on JSON, where a value is found by name and a repeated name takes its last value |
| **Backing a failing proof off** | two files where every row really has changed pay for a scan that never succeeds; retrying only every 64th row after 64 failures took that case from 5% to parity on wall |
| **Counting to the proof's end instead of parsing to it (guard_span)** | the proof's span needs one offset — through the delimiter ending the last compared column — but the join parsed every row fully to get it; counting those delimiters with the cursor alone skips the parse on proof hits: C 1.04x, C++ 1.07–1.12x, Zig 1.10x on 2M CSV; Rust neutral, its parser already cheap enough that the counting ate the win. Ships in all four ports |
| **Sizing hash-table slots to the row count** | one u64 per slot (40-bit position + hash tag) where 32 bits suffice; u32 slots save ~120 MB a side at 10M rows, ~500 MB at 50M: Rust 1.04x, Zig 1.07x on 2M CSV, kept for the memory more than the speed |
| **Deleting the dataframe engines from the Rust port** | a cold build went from twenty minutes to twenty seconds; nothing measured them any more |

Measured on `rust-zig-rewrite`, not here, and taken from
that branch's own record; what this project measured of them is the joint run in
[BENCHMARKS.md](BENCHMARKS.md), where its Zig does CSV in 4.55s and ndjson in
15.58s.

| Technique (other branch) | Verdict |
|---|---|
| **Not parsing every matched row twice** | the same finding the C port made independently, in both of those ports |
| **Sizing the index once and tagging its slots** | a failed probe is settled by the word already loaded; the C port had this, those two did not |
| **Joining both sides from one queue** | replaces two passes with one, and stops deep-copying the sorted rows |
| **Writing the index's zeroes rather than asking the kernel** | faulting a fresh mapping in costs more than touching memory already owned |
| **Prefetch distance 32** | their tuning; this port measured 24 on the same shape, so the optimum is a property of the machine as much as the code |
| **Huge pages on the slot table — on this host only** | 1.38s → 0.59s here, and a **loss** on theirs (+0.7% to +3.2% wall, CPU −3%, with the pages confirmed granted). One change, two machines, opposite verdicts: it is not general advice |
| **AVX-512** | wins on a CPU that has it, which hosted runners mostly do not — their own note says the 64-byte builds skip themselves |

#### Not worth it — measured, and recorded so it is not retried

| Technique | Verdict |
|---|---|
| **Huge pages in a loop** | each request makes the kernel compact memory. Two allocations win; six lose; sixteen lose badly. Column arrays 1.00s → 1.96s, key columns 2.03s → 2.79s (measured twice) |
| **Sharding the index insertion** | 2.84s against 1.95s, CPU 9.2s against 5.8s — the routing costs more than the serial insertion it parallelises |
| **Widening the hash to 8 bytes at a time** | no measurable effect |
| **A wave size other than 8,192 rows in the generator** | 2k, 32k and 131k all cost more on CSV (0.93s against 1.29s at 32k); ndjson is nearly flat, so the sensitive format chose it |
| **Splitting a row group's columns as the main Parquet lever** | 1.28x, against 2.0x for writing the two sides at once. Most of a Parquet run is the serial feeding of cell values into the column arenas, not the encoding |
| **Proving the row unchanged where nothing is ignored behind it** | *unsettled, and a lesson about the harness.* The column proof needs the last compared column's end, which is why this side is still parsed in full; where that column is the row's last, the line ending is the end and a key-only parse would do. First measured as 1.15x on a snapshot pair against 5-13% of CPU on the published shape, and reverted on that. Both halves were wrong: the paired estimator puts the gain at **1.09x (middle half 1.03-1.15)** and cannot establish the cost at all — 0.96x, middle half 0.90-1.01, still straddling 1.00 at 31 rounds. So it is a measured gain against a suspected 4% that thirty-one rounds could not resolve. Left out for now, and the reason is churn rather than the numbers |
| **Pipelining the serial insert against the sweep** | not built, and blocked by something other than what it looked like. The insert is serial for ordering, so overlapping it with the sweep looks free -- but it cannot start early for a different reason: `row_start`, `row_hash` and the table capacity are all sized from the *total* row count, which is only known once the last chunk is swept. The barrier is the allocation, not the order. Getting past it needs either a counting pass over the bytes first (~0.35s at 10M, against a ~0.09s prize) or a size estimate that reintroduces the rehash "sizing once" removed. And the prize shrinks with width: at 200 columns the insert is **1.4% of the run** |
| **A ceiling probe that removed more than it meant to** | the first attempt at pricing the insert skipped the insert loop, measured 2.08x of wall, and was meaningless: an empty index means an empty join, so it had priced both. `matched 0` in the output said so. A probe that removes a phase has to be checked against the counts it still produces, not just the clock |
| **A wider prefix compare for the byte proof** | 32 bytes a step instead of 8, four independent loads per branch. **No result at 20 columns and none at 200** -- and 200 is the case it was for, where a row is 1.6 KB and the proof scans nearly all of it. If four words a step is unmeasurable there, the compare is not what that loop is waiting on |
| **A shape cache for ndjson field names** | not built. A throwaway build that skipped the name lookup *entirely* -- unsound, but it bounds the prize -- was worth 6% of wall and 9% of CPU, and a real cache keeps less. Ten minutes of probe against a day of implementation. Re-probed after the byte proof and the key-only parse landed: **12% of CPU** now, because the same lookup is a larger share of a smaller run. Still not a day's work, and worth re-probing again rather than assuming either number |
| **Chasing a CPU regression that was noise** | an hour spent on a 1.9s→3.5s "regression" in the threaded generator that a nine-round measurement showed was 2.66s→2.61s. On this container a wall-clock difference under about 1.5x is not signal; use min-of-N CPU in one interleaved sitting |
| **Chasing a sweep gap that did not reproduce** | a 2M sitting measured C's sweep at 0.165s against 0.385–0.425s for the other three — a 2.5x parser lead, and the obvious next target. A fresh five-round run on the same machine put all four at 0.16–0.21s. The gap was machine load during the first sitting, written down before being re-run. Withdrawn in full |
| **GPU offload** | not attempted. Per-row cost doubles between 1M and 3M as the index leaves L3, putting the plausible crossover at 370k-4M rows — but every GPU-side number would have been an estimate, since there is no GPU here |

#### Things that were true and stopped being true

- **"The scan is bandwidth-bound, so more threads won't help."** Wrong, and one
  script disproved it: four copies of the single-threaded binary each finish
  *faster* than one alone (0.90x). The ceiling was the design.
- **"Input format matters less than the engine."** Wrong. Parquet took the same
  comparison from 23.25s to 4.89s — more than any engine change measured here.
- **"`shard` (Vector API) beats `turbo` (SWAR)."** True at 10M by 0.08s, which
  was noise on single runs. At twice the size SWAR is 19% ahead.
- **"The C port is fastest on every format."** True for about three hours. The
  other branch's rewritten Zig now takes ndjson, 15.58s against 20.13s.
- **"The C++ generator is faster than the C one and the gap stays."** Withdrawn:
  its Parquet row compared snappy output against uncompressed, and the host
  cannot measure that generator to better than a five-fold spread anyway.
